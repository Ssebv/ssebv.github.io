How I organize development: process and architecture

I organize software around three ideas: clear boundaries between parts, releases that can be checked, and production that reports its own health. This page shows the process, then the architecture of five real systems and why each one is built that way.

The processThe architectureThe rules

From plan to production

  1. Plan
  2. Short branch
  3. Tests in layers
  4. Review
  5. Staging
  6. Production
  7. Monitoring

  1. Write down how the project works

    Projects have a short document: how to install it, how to test it and what not to touch. Larger systems also keep one document per module, updated in the same commit as the code, and a record of architecture decisions with their trade-offs. Install and test steps from a public repo.

  2. Plan before risky work

    Anything large, or anything touching payments, production, tax documents or personal data, starts with a written plan before a single file changes.

  3. Work in short branches

    Each change is small enough to check on its own, with tests run after each block. Norte's iPhone app grew this way, in numbered rounds: tests, review, merge, deploy.

  4. Test in layers

    Types catch the cheap mistakes, unit tests the logic, database tests the access rules and end-to-end tests the full flow. Citofonía's CI runs all of them against a local database, and fails if the generated database types are out of date. Automated tests use test data and no real credentials. The ERP's critical flows are backed by about 180 test files, and I rehearsed its migration on a copy of production before the cutover.

    Replay of real commands.

  5. Measure what tests can't

    A passing test does not tell you whether an AI answer is good. For that I build evaluations and compare options on the same questions. In Odoo RAG, that is how I learned translation mattered more than hybrid search.

    Hybrid + translation82%

  6. Review, and check claims against the code

    Changes get a code review before they are committed, and a security review if they touch authentication, payments or personal data. It applies to what I write about my work too: a review found that my own article said a monitor ran every six hours, while the code said daily. I corrected the article.

  7. Ship in stages

    On the ERP, work moves from a development branch to staging and then to production. Production deploys happen only outside business hours in all three countries, because a build restarts the server. For the migration, I compared the result against a pre-upgrade baseline: invoices, orders and deliveries were identical.

  8. Watch it in production

    A daily health check runs over 40 detectors, with urgent alerts every 30 minutes. I wrote about what it found, including the detector of mine that was confidently wrong.

Architecture of five systems

Each system has different constraints, so each one has a different shape. The diagrams read from top to bottom, from the people using the system down to where the data lives. The highlighted part is the one that defines the design.

ERP on Odoo 19

A production ERP for 4 companies in 3 countries, hosted on Odoo.sh. The source is private.

  1. Channels
    • Back office
    • Retail consignment
    • Mercado Libre
    • Yuju
  2. 18 custom modules
    • Shared core: sales, stock, invoices
    • Consignment
    • Invoicing by delivery
    • Reports
  3. Tax localization
    • Chile · SII
    • Colombia · DIAN
    • Peru · SUNAT
  4. Platform
    • Odoo 19
    • PostgreSQL with invariants
    • Health check and alerts
  • Fewer modules, clearer ownership. I consolidated 41 custom modules into 18, so there is less to upgrade and shared logic has one home.
  • Critical rules live in the database. A PostgreSQL trigger enforces the consignment stock invariant, so no code path or script can skip it.
  • Explicit fields, not naming conventions. A warehouse reorganization had to update 45 places in 7 modules that relied on location names. The rule now is to identify consignment by a field.

Citofonía

A digital building intercom, in development, with its own page. It is a monorepo with pnpm and Turborepo: a mobile app, an admin panel, an API and shared packages for database types and UI. The source is private.

  1. Clients
    • Resident app · React Native, Expo
    • Concierge tablet
    • Admin panel · React, Vite
  2. API on the edge
    • Hono on Cloudflare Workers
    • Calls
    • Doors
    • Push
    • Invitations
    • Votes
  3. Call state
    • One Durable Object per unit: the call
    • One per station: the call limit
  4. Data and media
    • Supabase PostgreSQL with row-level security
    • LiveKit for calls
  • The database enforces access. For everyday data, the apps talk to PostgreSQL directly, under row-level security tested with pgTAP. The API handles what the database cannot, such as calls, doors, push and invitations.
  • The call lives on the server, not on a device. Each apartment has a state machine in a Durable Object, with its own alarms. Tests run the same logic through an in-memory version.
  • Door hardware sits behind one interface. A driver has one method, openDoor. Today there are two, for the tablet and for an HTTP relay, and a new door system means a new driver.
  • Migrations are never edited. There is one per topic and 105 so far. Types are generated from the schema, and CI checks they are current.

Norte

A personal finance and health app with native and web clients. The source is private.

  1. Clients
    • iPhone, Apple Watch and widgets · SwiftUI
    • Web · Next.js, React
  2. API
    • One REST JSON API for every client
    • Session check on each request
  3. Domain
    • Finance
    • Training
    • Nutrition
    • Habits
  4. Data and services
    • SQLite
    • Bank email reader · IMAP
    • Anthropic API, validated output
  5. Hosting
    • VPS
    • Caddy
    • systemd
  • One API for every client. The iPhone and the web use the same endpoints, so a business rule is written once.
  • No third-party dependencies on iOS. The app uses only what the platform provides, so there is nothing to update or audit from outside.
  • A single-file database. A single-user app does not need a database server. SQLite keeps hosting and backups simple.
  • Screen tests are isolated. They run against a local server with a temporary database and demo data, and refuse to run against production.

FlagForge

Multi-tenant feature flags in Rust. It has its own page, and the source is public.

  1. Clients
    • Service SDK
    • Dashboard · Leptos, WebAssembly
    • Operators and CI
  2. API · axum
    • Evaluation, from memory
    • Management API
    • Snapshot cache
  3. Engine
    • flagforge-core: pure functions, no I/O
  4. Data
    • flagforge-storage: SQL checked at compile time
    • PostgreSQL, LISTEN/NOTIFY
  • The part that must be correct has no I/O. Evaluation is a pure function of the flag, the context and the environment (salt and segments), so it can be tested thoroughly.
  • One engine, three consumers. The server, the SDK and the dashboard's rule editor reuse the same crate, so they cannot disagree.
  • A schema change breaks the build, not production. sqlx verifies every query against the real schema at compile time.

ModoMax

An online store. Its assistant decisions have their own page. The source is private.

  1. Clients
    • Storefront
    • Admin panel
    • WhatsApp
  2. Application
    • One Next.js app: pages, server actions, API routes, scheduled jobs
  3. Domain and validation
    • Prisma
    • Zod
    • Audit log
  4. Data and services
    • PostgreSQL, local access only
    • Payments
    • Tax documents
    • Email
    • Anthropic API
  5. Hosting
    • VPS
    • Caddy
    • systemd
  • One deployable app. For a store this size, a single application on a VPS is easier to run and debug than separate services.
  • The database is not exposed. PostgreSQL accepts local connections only.
  • Schema changes go through migrations. Production uses prisma migrate deploy, never db push.

Rules I keep

  • No deploys to the ERP's production during business hours in any of its three countries.
  • Secrets stay out of repositories.
  • A committed migration is never edited.
  • Automated tests never touch production, and sample data is always fictional.
  • Changes that are hard to undo get an explicit decision first.
